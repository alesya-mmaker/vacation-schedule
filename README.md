# График отпусков — прототип

Прототип автоматизирует проверку заявлений на отпуск по внутреннему регламенту компании и Трудовому кодексу РБ. Сотрудник подаёт заявление через одну форму, система проверяет его по правилам, а HR (РО1) видит готовый чек-лист и принимает решение.

- **Приложение:** https://vacation-schedule-nu.vercel.app
  - форма для сотрудников: https://vacation-schedule-nu.vercel.app/form
  - раздел HR: https://vacation-schedule-nu.vercel.app/hr (вход по email и паролю; доступ передаётся отдельно, не в репозитории)
- **Данные вымышленные**, структура компании смоделирована по тексту регламента.
- Ничего устанавливать не нужно: прототип работает по ссылке, путь по нему описан ниже.

## Проблема

Сейчас РО1 вручную собирает пожелания сотрудников, сверяет даты с регламентом и законом, ищет пересечения (кто с кем не может быть в отпуске одновременно) и просит сотрудников перенести даты. Это долго, легко пропустить пересечение, а правила живут в голове и в документе.

## Решение

### Для сотрудника

1. Открывает форму (ссылка без входа), находит себя в списке по фамилии, выбирает тип, даты и заместителя. В списке заместителей только «свои»: руководитель, коллеги и подчинённые.
2. Отправляет и видит «Заявление принято, HR рассмотрит его». Ничего не проверяет сам, правила ему не показываются.
3. Получает сообщение о решении. При отказе в сообщении есть причина и ссылка на форму исправления: ФИО уже подставлено, после отправки прежнее заявление заменяется новым, история сохраняется. Ссылка одноразовая, вместо номеров в ней случайный код.

### Для HR

- **Заявки:** список с цветом проверки (зелёный — всё выполнено, жёлтый — предупреждения или возможные конфликты, красный — нарушения), пометкой «новая» для ещё не открытых, фильтрами по статусу и подразделению и поиском по ФИО. Фильтры сохраняются в адресе страницы.
- **Карточка заявки:**
  - чек-лист всех применимых правил: что выполнено, что нет и почему, с именами и датами конфликтующих сотрудников и источником правила;
  - история корректировок и журнал событий с датой и временем;
  - кнопки «Согласовать», «Отклонить», «Согласовать как исключение» (комментарий обязателен). При нарушении обычное согласование недоступно, только исключение.
  - перед отправкой показывается сообщение сотруднику по шаблону, его можно поправить.
- **График:** сотрудники по подразделениям, месяцы по горизонтали, отпуска полосами цвета статуса. Нарушения обведены красным, дни, из-за которых нарушение, заштрихованы. Подразделения сворачиваются, есть поиск сотрудника.
- **Правила:** включить или выключить, изменить параметры и уровень, добавить новое правило из готовых видов проверок, справочник типов заявлений. После любого изменения все заявки пересчитываются и видно, у кого изменился цвет.
- **Шаблоны** сообщений с подстановками `{ФИО}`, `{даты}`, `{причина}`, `{ссылка}`.
- **Исходящие:** журнал сообщений сотрудникам. Реальной отправки в прототипе нет.
- **Сотрудники:** добавление, изменение, удаление. При удалении удаляются его заявки и сообщения, а у других очищаются ссылки на него (руководитель, заместитель); после этого всё пересчитывается.

## Как пройти по прототипу

**Путь сотрудника.** Откройте форму `/form`, начните вводить фамилию (например, «Павл») и выберите сотрудника. Укажите даты и заместителя: в списке только руководитель, коллеги и подчинённые этого человека. Отправьте — заявление сразу появится у HR с пометкой «новая».

**Путь HR: проверка и решение.**
1. Войдите в `/hr`. Во вкладке «Заявки» новые заявки выделены, рядом с вкладкой — их число.
2. Откройте заявку №6: ИД просит отпуск, когда в отпуске ЗАВ. В чек-листе видно нарушенное правило, ЗАВ с датами и пункт регламента; обычное согласование недоступно, только отказ или исключение с комментарием.
3. Нажмите «Отклонить», укажите причину — откроется сообщение сотруднику по шаблону со ссылкой на исправление. После отправки оно появится в «Исходящих».
4. Откройте ссылку из сообщения: форма уже знает сотрудника и прежние даты. Новое заявление заменит прежнее, а в карточке появятся история корректировок и журнал. Готовый пример такой цепочки — заявки №10 и №11.

**Путь HR: правила.** Во вкладке «Правила» откройте «МПП: не более 2 в отпуске одновременно», поставьте лимит 3 и сохраните. Все заявки пересчитаются, и над таблицей появится: «№3 Егорова Ксения Михайловна: красная → зелёная». Верните лимит 2 — заявка снова станет красной.

**Путь HR: график.** Во вкладке «График» в «Отделе продаж» видно трёх МПП в марте: заштрихованы 10–14 марта — дни, когда лимит превышен. Клик по полосе открывает заявку.

## Какие правила автоматизированы

Правила не зашиты в код. В базе хранятся вид проверки и параметры, HR меняет их в интерфейсе. Проверка идёт против согласованных заявок. Пересечение заявки на рассмотрении с другими заявками на рассмотрении показывается как «возможный конфликт», а не как нарушение.

| Правило | Источник | Вид проверки | Уровень |
|---|---|---|---|
| МПП: не более 2 в отпуске одновременно | Регламент, п.1 | лимит одновременно | нарушение |
| Менеджер секции: не одновременно с менеджерами секций своего отдела и НО | Регламент, п.1 | нельзя одновременно с … | нарушение |
| НО: не одновременно с другими НО своего отделения и РО | Регламент, п.1 | нельзя одновременно с … | нарушение |
| РО: не одновременно с другими РО того же ЗАВ/ЗТВ и с ним самим | Регламент, п.1 | нельзя одновременно с … | нарушение |
| ЗАВ, ЗТВ: не одновременно с ИД | Регламент, п.1 | нельзя одновременно с … | нарушение |
| ИД: не одновременно с ЗАВ и ЗТВ | Регламент, п.1 | нельзя одновременно с … | нарушение |
| Заявление не позднее чем за месяц (30 дней) | Регламент, п.2 | срок подачи | нарушение |
| Указан заместитель, и он сам не в отпуске | Регламент, п.2 | заместитель | нарушение |
| Перенос согласованного отпуска не позднее чем за 14 дней | Регламент, п.5 | срок переноса | нарушение |
| Летом (1.06–31.08) не более 14 дней | Регламент, п.6 | длительность в период | нарушение |
| Заявление до срока графика (15.01 и 15.07), иначе «вне графика» | Регламент, п.4 | срок графика | предупреждение |
| Хотя бы одна часть отпуска не менее 14 дней | ТК РБ, ст.174 | часть отпуска | предупреждение |
| Запланировано X из 24 дней основного отпуска | ТК РБ, ч.1 ст.155 | норма в году | информация |

Всего 9 видов проверок. Новое правило HR собирает из любого вида, например «С 25.12 по 10.01 не более 7 дней». Длительность считается в календарных днях.

**Что нельзя без программиста:** придумать новый вид проверки (например, «не более 30% отдела»). Лимит считается по всей компании, а не по подразделению. «Нельзя одновременно с …» опирается на руководителя, указанного у сотрудника.

## Допущения и решения

- Структура компании смоделирована по тексту регламента: уровни (дирекция → отделение → отдел → секция) и подчинённость (ИД → ЗАВ/ЗТВ → РО → НО → менеджеры секций) выведены из п.1. Названия подразделений («Отделение «Центр»», «Отдел №1», «Отдел продаж» для МПП) и все сотрудники вымышлены.
- Должности названы сокращениями, как в регламенте.
- Уровни правил: в регламенте их нет. «Вне графика», «часть отпуска 14 дней» и «24 дня» мягкие по постановке задачи; остальные пункты регламента обязательны, поэтому это нарушения. HR может поменять уровень любого правила.
- У решённых заявок возможные конфликты не показываются: они нужны только для заявок, по которым HR ещё принимает решение.
- Заявка, согласованная как исключение, не делает нарушителями уже решённые заявки других сотрудников (превышение разрешил HR), но новые заявки на те же даты учитывают её как обычный согласованный отпуск. Само исключение остаётся красным по чек-листу, чтобы было видно, что именно разрешено.
- «Коллега» для выбора заместителя — сотрудник с тем же руководителем и той же должностью или из того же подразделения.
- Пометка «новая» общая для всех HR: открыл один — пропала у всех.
- Удаление сотрудника удаляет и его заявки, и сообщения ему. Архив кадровых документов в рабочей версии ведётся в 1С — там же учитываются сроки их хранения.
- Сотрудник в форме не входит в систему, а выбирает себя из списка, поэтому теоретически может подать заявление за другого. Подменить чужую корректировку нельзя: ссылка содержит случайный одноразовый код. В рабочей версии нужен вход сотрудников (см. «Развитие»).
- Ограничения формы повторяет база, поэтому обойти их, отправив заявление в обход формы, нельзя. База проверяет:
  - тип заявления — только действующий;
  - заместителя — только «свои»;
  - начало — не в прошлом, конец — не дальше двух лет;
  - комментарий — до 1000 символов.
- Защита от рассылки скриптом: не больше 5 заявлений от одного сотрудника за час и 30 от всех вместе за минуту. Общий лимит можно намеренно исчерпать и на минуту закрыть форму для всех. В рабочей версии его заменит вход сотрудников.
- Если несколько HR работают одновременно, по заявке принимается только первое решение. Решение по уже обработанной или заменённой заявке база не примет, и HR увидит, что нужно обновить страницу.
- Регламент компании (`reglament.docx`) в репозиторий не включён как внутренний документ.

## Технологии и почему

| Что | Зачем |
|---|---|
| React + TypeScript + Vite | быстрый интерфейс без перезагрузок; типы ловят ошибки до запуска |
| Tailwind CSS | аккуратный интерфейс без отдельной вёрстки стилей |
| Supabase (PostgreSQL) | готовая база, вход и правила доступа без собственного сервера |
| Vercel | публикация по ссылке, автоматически при каждом изменении в GitHub |
| Vitest + PGlite | тесты модуля правил и тесты базы на тех же SQL-файлах, что в Supabase (PostgreSQL прямо в памяти) |

**Облачные сервисы используются в прототипе, архитектура готова к переезду на свои серверы.**
- Все обращения к базе и ко входу собраны в одном слое `src/data/`; экраны и модуль правил о Supabase не знают (это проверяет линтер).
- Модуль проверки правил (`src/rules/`) — чистые функции без базы.
- Правила доступа написаны на обычном PostgreSQL (RLS) и переезжают вместе с базой.

### Устройство проекта

```
src/
  rules/      модуль проверки правил (9 видов проверок) + тесты
  domain/     предметная логика: типы, сообщения, журнал, «свои» сотрудники, виды правил
  data/       слой доступа к данным (единственное место, где есть Supabase)
  state/      общие данные приложения, пересчёт и сохранение результатов проверки
  pages/      экраны: форма сотрудника, вход, раздел HR
supabase/
  schema.sql, seed.sql      схема и тестовые данные
  migrations/002…011        доступ, функции формы, справочник типов и т.д.
tests/        тесты на базе (те же SQL-файлы во временном PostgreSQL)
```

## Развитие

- **Вход по корпоративным аккаунтам** для HR и сотрудников: ФИО в форме подставляется автоматически, подать за другого нельзя.
- **Переезд на свои серверы в Беларуси.** Персональные данные лучше хранить там, где работает система. Заменяется только слой `src/data/`. Варианты входа: развернуть Supabase (open source) у себя — приложение не меняется; Keycloak + корпоративный Active Directory; свой сервер с логинами в PostgreSQL.
- **Интеграция с 1С:** список сотрудников, структура подразделений и архив документов приходят из 1С, HR не ведёт два списка.
- **Реальная отправка сообщений.**
  - *Email:* адреса сотрудников, почтовый сервер компании (SMTP) или сервис рассылки и серверная функция отправки (ключ нельзя хранить в браузере).
  - *Telegram:* бот компании; каждый сотрудник один раз нажимает «Старт» по личной ссылке.
  
  В обоих случаях «Исходящие» остаются журналом.
- **Учёт государственных праздников** (сейчас длительность в календарных днях без праздников) и **остатков отпуска**.
- **Автоподбор дат:** при отказе предложить ближайшие даты той же длительности, которые проходят все правила.
- Автор действия в журнале заявки, если HR несколько; уведомление HR о новых заявках.

## Запуск у себя (для разработчиков)

Для просмотра прототипа ничего устанавливать не нужно — он работает по ссылке выше. Этот раздел нужен, только если хочется развернуть копию со своей базой.

Нужны Node.js 20+ и бесплатный проект в [Supabase](https://supabase.com).

1. **База.** В Supabase → SQL Editor выполнить по очереди:
   `supabase/schema.sql` → `supabase/seed.sql` → все файлы `supabase/migrations/` по номерам (002…011).
2. **Вход HR.** Authentication → Sign In / Providers: выключить «Allow new users to sign up». Затем Authentication → Users → Add user: email и пароль для HR, отметить «Auto Confirm User».
3. **Ключи.** Скопировать `.env.example` в `.env.local` и вставить Project URL и anon public key из Project Settings → API. Необязательно: `VITE_PUBLIC_URL` — публичный адрес приложения для ссылок в сообщениях сотрудникам.
4. **Запуск:**
   ```bash
   npm install
   npm run dev
   ```
   Приложение откроется на http://localhost:5173: `/form` — форма, `/hr` — раздел HR.
5. **Тесты** (база для них поднимается в памяти, Supabase не нужен):
   ```bash
   npm test
   ```
   106 тестов: каждый вид правила, тестовые данные и сценарий с лимитом МПП, доступ без входа и проверки при подаче заявления, решения HR, удаление сотрудника, журнал, установка базы с нуля по этой инструкции.

**Публикация:** импортировать репозиторий в Vercel, указать переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. `vercel.json` уже настраивает прямые ссылки.
